# شلّتك ولوحة الشرف — المرحلة الخامسة التجريبية

**هذه مواصفات القبول الأصلية وليست إيصال نجاح.** نتائج سبرنت Beta الجديدة وحدودها في [تقرير التحقق](beta-readiness-verification.md)؛ لا تنتقل موافقات المرشحين السابقين إلى مصدر PR #13. هذا الفرع متراكم فوق Draft PR #12 عند الرأس `35d970c3b91246e850dda23b6adeee93213889b6`. نجاح المرحلة الرابعة السابق لا يتحقق من هذه الإضافة. لا موافقة دمج أو نشر أو بيانات حقيقية.

## ما الذي بُني؟

- شلّة خاصة اختيارية مرتبطة بمالك حساب قدّام، وعضويات `OWNER / MEMBER` لحسابات مسجلة فعلًا؛ لا يجري تحويل اسم RSVP المجهول إلى حساب أو عضوية.
- فريقان ثابتان بأسماء مطبّعة بعد إنشاء الشلّة. **لوحة شرف الفرق** تعرض عدد بطولات الليلة والنقاط التراكمية والسهرات المرتبطة. لا توجد شارات انتصارات شخصية أو ادعاء بمعرفة أعضاء كل فريق؛ محركات Night الحالية لا توثق عضوية اللاعب داخل الفريق عبر السهرات.
- بحد أقصى 5 شلل يملكها الحساب، و20 حسابًا لكل شلّة (بمن فيهم المالك)، و5 روابط عضوية نشطة في وقت واحد. الدعوة 256 بت عشوائي، أحادية الاستخدام وصالحة 7 أيام، ولا يُحفظ نص الرابط، فقط SHA-256؛ يعرض مرة واحدة للمالك. حاملها لا يستطيع الانضمام دون حساب وتأكيد POST من نفس Origin. يمكن للمالك إلغاء دعوة نشطة بواسطة معرف سجلها دون كشف الرمز. الرابط قابل لإعادة التوجيه: أول حساب مؤهل يؤكده يستهلكه. لا إرسال واتساب/بريد آلي ولا حماية شاملة من الطلبات الموزعة.
- قائمة الأعضاء لا تُعرض إلا لعضو مسجل في الشلّة، وتظهر أسماء الحسابات عن علم بالانضمام. مغادرة العضو تزيل صف عضويته وتحجب وصوله فورًا؛ لا يستطيع المالك المغادرة دون قرار نقل ملكية. الأرشفة تمنع أعضاء جددًا ونتائج جديدة، وتترك التاريخ للقراءة؛ **الأرشفة ليست محو بيانات**.
- ربط سهرة مكتملة يتطلب اختيار المالك الصريح، وملكيته لكل من الشلّة والسهرة، واكتمال الألعاب الثلاث الرسمية وإيصالاتها المعتمدة، وتطابق أسماء الفريقين وترتيبهما مع فريقي الشلّة. تُعاد اشتقاق النقاط من الإيصالات المقبولة بقاعدة Night نفسها؛ لا يقبل API نقاطًا أو فائزًا أو معرف هوست يرسله المتصفح. لا تُحسب السهرة الناقصة. التعادل يمنح كلا الفريقين المتعادلين بطولة ليلة؛ ترتيب الشلّة يقاس أولًا بعدد بطولات الليل ثم بالنقاط، مع Competition Ranking للتعادل. تحسب كل سهرة مرة واحدة **عبر كل الشلل** بواسطة قيد `nightId UNIQUE`، والإعادة المطابقة في الشلّة نفسها لا تضاعف الأثر.
- لقطة النتائج `ShillaNight` بعد قبولها محفوظة وغير قابلة للتعديل/الحذف بواسطة trigger PostgreSQL؛ الربط لا يغيّر نتيجة Night الأصلية أو رسائل الدفع. واجهة الأعضاء لا ترد بمعرفات جلسات Night أو إجابات الألعاب أو مفاتيح الدعوة أو معرفات الحسابات.
- صفحة شللي `/shillatak`، وصفحة مجموعة `/shillatak/[id]`، وصفحة قبول دعوة `/shillatak/join/[code]`؛ واجهات API تحت `/api/shillatak`. شروط `ENABLE_NIGHT_OF_QUDDAM=true` **و** `ENABLE_SHILLATAK=true` معًا، وكلاهما غير مفعل افتراضيًا. صفحة رابط الانضمام `private, no-store` و`no-referrer` و`noindex`.

## تغييرات التخزين

`prisma/migrations/20261016020000_shillatak_mvp/migration.sql` إضافة فقط: `Shilla`, `ShillaMembership`, `ShillaTeam`, `ShillaInvite`, `ShillaNight` مع مفاتيح وعلاقات وقيود، وفهرس مالك واحد، وtrigger عدم تغيير سجل البطولات. أُضيفت علاقات Prisma إلى `User` و`NightSession` دون تعديل migrations السابقة أو الرصيد أو محركات الألعاب. لا يحفظ سجل الدعوة المستهلكة معرف حساب من استعملها؛ فقط تاريخ الاستهلاك. تبقى عضويات الحسابات وتاريخ نتائج المجموعات بيانات شخصية/شبه شخصية تتطلب سياسة احتفاظ مستقلة.

## بوابة القبول المطلوبة — ليست نتائج منفذة

استخدم أحدث **SHA حرفي** من فرع هذه المهمة في checkout نظيف، وقاعدة PostgreSQL 17 جديدة معزولة على loopback وحسابات/أسماء اصطناعية. لا تشغّل `db:migrate` قبل التحقق من قاعدة الهدف الجديدة وعدم اتصالها بالإنتاج.

```sh
cd qalba-platform
npm ci
npm run db:generate
# ONLY with fresh isolated synthetic PostgreSQL 17 DATABASE_URL:
npm run db:migrate
npx vitest run src/lib/shillatak/rules.test.ts src/app/api/shillatak/route.test.ts src/proxy.test.ts --reporter=verbose
npm run test
npm run typecheck
npm run lint
npm run build
```

أضف وشغّل اختبارات تكامل PostgreSQL أصلية وتجربة Google Chrome حقيقية (ليست mock) تشمل:
1. منشئ يسجل دخولًا وينشئ شلّة باسم وفريقين متمايزين؛ رفض الاسم المشوش وتكرار اسمي الفريقين بعد التطبيع، ورفض المجموعة السادسة تحت تنازع معاملات حقيقي.
2. حساب ثانٍ لا يستطيع قراءة شلّة ليس عضوًا فيها. المالك ينشئ دعوة؛ لا يُحفظ نصها؛ يفتحها حساب ثاني ثم يقبل مرة واحدة. سجّل وصول العضو ورفض إعادة استخدام الرمز من ثالث، وإلغاء دعوة أخرى قبل استخدامها، وانتهاء صلاحيتها وإبطال دعوات الأرشفة. تحقق من حد 5 روابط نشطة و20 عضوًا تحت JOIN متزامن.
3. متصفح ثانٍ يرى ترتيب الفرق والتاريخ وأسماء الأعضاء المعلن عنها داخل المجموعة فقط، لكن لا يرى أدوات المالك أو دعوة المالك الخام، ولا يستطيع تنفيذ INVITE/ATTACH/ARCHIVE/REVOKE باسم المالك. عضو يغادر؛ قراءة المجموعة بعدها 404. المالك لا يستطيع LEAVE حتى تُعتمد سياسة نقل الملكية.
4. أنشئ Night حقيقية بمحركات `top-list` (5 جولات)، `ordering-challenge` (7)، `survey-show` (5). سجّل نتائجها الأصلية و`IMPORT` حتى `completed`. تظهر للمالك فقط سهرة مطابقة الفريقين؛ اربطها صراحةً؛ تأكد من النقاط وبطولة ليلة واحدة وخصومات START الثلاثة السابقة فقط، و**صفر خصم** للربط أو العضويات أو الدعوات.
5. اختبر تعادلًا نهائيًا موثقًا من إيصالات Night فتُمنح بطولة لكل بطل مشترك؛ ثم سهرة مستقلة لإثبات الترتيب عبر الليالي. رفض سهرة غير مكتملة، أو مالك مختلف، أو أسماء فرق مختلفة، أو إيصال مفقود أو متعارض، أو إدخال نقاط أو ownerId مزيف. ربط السهرة نفسها مرتين في الشلّة لا يضاعف النتائج؛ ربطها في شلّة أخرى يُرفض.
6. اختبر parallel attach على PostgreSQL اتصالات مستقلة وحد `nightId UNIQUE` وسلامة snapshot trigger عند UPDATE/DELETE، وقيّم rollback للـmigration فقط على قاعدة اختبار جديدة لا تحتوي نتائج حقيقية.
7. اعزل التخزين عن نتائج Night القديمة: تعطيل علم الشلّة يعيد 404 للصفحات/API دون كشف بيانات، ولا يعطل نظام Night أو الألعاب منفردة. refresh/restart يجب أن يحفظ العضوية والنتيجة. شغّل Chrome لمسارات إنشاء الشلّة، الرابط، الانضمام، بطولة الليلة، لوحة الشرف، الإلغاء، الأرشفة والمغادرة.
8. افحص ربط المصدر حرفيًا `git` commit/tree وملفات الاختبارات قبل/بعد، واحتفظ بالأدلة الخاصة (لا تنشر raw tokens، معرفات حسابات أو cookies، أو trace فيه مفاتيح سرية).

## المتبقي قبل الإطلاق

- **سياسة احتفاظ وحذف وتصدير وطلب محو** لبيانات العضوية وروابط الدعوات والسجلات غير القابلة للتعديل، وقرار نقل ملكية الشلّة إذا أراد المالك المغادرة. الوضع الحالي يسمح للعضو بمغادرة المجموعة والأرشفة للمالك، لا ينفذ محوًا دائمًا للنتائج المعتمدة، فلا تدّع اكتمال متطلبات الخصوصية.
- دعوات المجموعة ليست إثباتًا لهوية شخصية تتجاوز تسجيل حساب قدّام؛ الرمز قابل للمشاركة ويستهلكه أول مستخدم مقبول. يلزم تقييم الإساءة والقدرة القصوى في نشر حقيقي، وتقييم محدودية 5 شلل/20 عضوًا.
- بوابات HTTPS وتشغيل الإنتاج والنقل الفعلي LAN/NAT وتحسينات الأمان/الاعتماديات والمراقبة/التنبيه والبوابات المالية والإطلاق الرسمي ما زالت مستقلة، تمامًا كما في PR #9 و#10 و#12.
- لا موارد خارجية، ولا إنشاء خادم أو دفع حي، ولا دمج، ولا تعديل لـmain أو PRs السابقة. الإنفاق الخارجي الإضافي $0.

هذا المستند يصف بوابة القبول، ولا ينسب تنفيذًا إلى أمر مكتوب فقط. راجع [تقرير Beta](beta-readiness-verification.md) وإيصال الرأس الحرفي المنشور على PR #13 للأعداد الفعلية ونتائج PASS / PARTIAL / FAIL / NOT RUN. أسماء الشلل المعروضة ليست معرفات فريدة؛ اختلاف اسمي الفريقين بعد التطبيع هو الشرط المعتمد. حد المجموعات الخمس يشمل المجموعات المؤرشفة. لم تُنفذ سياسة حذف أو نقل ملكية جديدة.
