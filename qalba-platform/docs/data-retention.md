# Quddam data retention — technical product policy (Phase 5.0E-1)

This policy implements M12 on the completed D-3 baseline. It is a technical product policy, not a statement of Saudi or other legal compliance. It preserves the ten games, financial audit, immutable authored snapshots, original auth semantics and supported profile/history results. No production cleanup is performed by deployment, migrations or app startup.

## Implemented policy

All ages use UTC instants and strict `< cutoff`; a record exactly at its cutoff survives until the next invocation. Invalidation means expiry or an already recorded revocation/use. Active games include LOBBY, READY, IN_PROGRESS and PAUSED; terminal means persisted COMPLETED/ABANDONED **and non-null endedAt**, with a compatible terminal state (phase COMPLETED/ABANDONED/DONE or Category Board completed=true). Unknown or contradictory active state is retained. Cleanup never changes GameSession.state, stateVersion, scores, wallet, room lifetime or auth validity.

Credential grace does not extend authorization: expiry/revocation is enforced immediately by existing H01/H02 checks. Expired access belonging to an active game is conservatively deferred until that game is terminal; we do not auto-abandon old games in this phase. User suspension alone is not a cleanup trigger; ordinary fixed session expiry still bounds the row without changing unsuspension semantics.

A 90-day private-vote cleanup preserves only counts, not a copied voter/choice table. Social retains counts per ballot; the existing state already holds the disclosed tally. Court retains count while original aggregate verdict/scoreAudit remains. During partial batches views sum remaining live count plus retained count, so visible counts stay exact. Rows/word snapshots and result scores are not rewritten. After a supported later rematch a new round uses default zero/empty counts and normal rules.

Some private-looking data is intentionally retained because it is part of supported results: Social reveal word/accepted aliases/outsider/guess, Ranked entries revealed at results, Letter lastAnswer, Survey Host/result answers, Court aggregate verdict, Bluff disclosed answer ownership/voterIds/scoring and moderation references. Unknown legacy PlayerResponse/RoomVote dependencies are retained conservatively. This phase does not claim all authored secrets or identities are erased; it bounds obsolete access and unneeded Social/Court private links without destroying required history.

## Stored state, infrastructure and other artifacts

- All authoritative gameplay state/deadlines and immutable snapshots live in PostgreSQL GameSession/GameRound and game-specific use/round rows. They are retained; no client-only state is converted or lost.
- SSE connection slots, timers, backpressure queues and retry state are process-local D-1 objects, already released on disconnect/abort. No SSE lease/token cache table exists. Cleanup does not change marker polling, caps or backoff.
- AuthAttempt keys are secret-HMAC pseudonyms. No raw IP/client address is persisted by M05; cleanup output never contains one. Existing password/email/account records remain necessary for account ownership.
- PaymentEvent stores allowlisted identifiers/source/outcome, not raw callback bodies/card data/tokens. Purchase retains UNKNOWN_OUTCOME intent and PENDING leases/next eligibility until actionable reconciliation resolves them. PurchaseRefund retains unresolvedCredits/supportStatus/operator evidence. No financial row or metadata is modified.
- Admin content is the authored bank; there is no generic admin audit table. BluffModerationAudit and financial support PaymentEvent operator information are retained. QuestionReport may contain user-provided report detail and stays available for moderation; no speculative deletion of unresolved support data.
- CSV import bodies are bounded/processed in memory; no import/export/recovery staging table exists. Local generated ZIPs, logs, test reports and deployment backups are outside the database job. Keep them under separately managed storage access/lifecycle controls; no backup-deletion/compliance guarantee is claimed here.

## Cleanup architecture and bounds

Internal command only:

```bash
node --import tsx scripts/data-retention.ts --dry-run --batch-size=100
node --import tsx scripts/data-retention.ts --batch-size=25
```

Production cron recommendation: **daily**, one `--batch-size=100` invocation (maximum accepted 500). This is a documented schedule, not an infrastructure deployment. Operators need restricted application DATABASE_URL access; no public retention API or deletion UI was added. Keep database credentials outside logs/cron command-line arguments. The existing authenticated analytics cron remains authenticated and now invokes the same bounded analytics policy (at most 500 targets).

One global candidate budget applies across all fourteen target kinds; not 100 per table. Query retrieves at most budget+1 metadata rows. Processing touches at most budget logical target records, with one short transaction per target (`maxWait` 2s, `timeout` 5s). A vote deletion additionally updates exactly one round count in that same transaction, so SQL writes are at most twice the target count. There is no loop until backlog is empty. Overall runtime also depends on DB health; do not advertise a wall-clock SLA. Failure of one target rolls back that target and increments failed, preserving earlier committed records.

Order is `(eligibleAt, kind COLLATE C, id COLLATE C)`; optional base64url `--cursor=<nextCursor>` resumes strictly after the last scanned tuple. Cursor contains only internal row metadata, not payloads or hashes; treat operational output as internal. Daily runs **omit cursor** to revisit skipped/locked/failed rows. Continuations reduce manual backlog in explicitly bounded runs, not an unbounded loop. Oldest-first candidates disappear after successful cleanup; active records never enter eligibility. Monitor backlog: a daily 100 budget is deliberately conservative and may require approved additional bounded invocations if creation exceeds cleanup.

Normal mutation locks are `GameSession -> Room -> target`, using `FOR UPDATE SKIP LOCKED`; then exact eligibility and unchanged parent identities are re-read under READ COMMITTED. A lifecycle change committed before locks is observed and skipped; a change after cleanup locks serializes after the cleanup transaction. This is the same parent lock used by game commands. Two cleanup workers cannot double-increment retained vote counts or delete/redact twice. Auth/reset target locks likewise protect renewed/ineligible rows. No long transaction spans a batch. Dry run repeats the eligibility check with no write statements or write locks and returns aggregate candidates/actions; it is a point-in-time preview, not a reservation or promise that later eligibility remains identical.

Output: scanned, eligible, deleted, redacted, skipped, failed, per-kind counts, hasMore and opaque continuation. Dry-run deleted/redacted always zero. No deleted private values, token hashes, command bodies, passwords, full DB error messages or per-record permanent logs are emitted. Exit status is nonzero on aggregate per-record failures or invocation failure. Monitor skipped separately from failures: busy parent locks are normal retryable skips.

## Migration and query support

One forward migration `20261006170000_operational_data_retention`: SocialRound.retainedVoteCounts JSONB default `{}`; CourtRound.retainedVoteCount integer default 0; object/nonnegative constraints; expiry indexes on auth/reset/room/access classes, partial invalidation-time indexes, and GameSession(status,endedAt,id). Existing AuthAttempt(windowStart), analytics occurrence/name indexes, participant session/round vote indexes support remaining branches. Defaults preserve existing reads; no historical snapshot backfill/private deletion occurs in migration. Partial index definitions live in SQL because Prisma does not declare their predicate here.

Representative EXPLAIN evidence is recorded by the native test on 2000 non-expired auth rows. It verifies an indexed narrow eligibility branch, not production capacity or a full-table scale benchmark; M13 remains separate. Before large production index installation, assess expected table size and deployment maintenance requirements.

## Rollout, monitoring and recovery

1. Back up the database under existing restricted operational practice; deploy migration/code. No automatic cleanup occurs.
2. Run dry-run only, `--batch-size=100`; inspect aggregate candidate classes and expected ages.
3. Confirm business/product approval for the implemented technical windows and financial records being excluded.
4. Run one small real batch, `--batch-size=25`.
5. Verify representative profile/result routes, account login/revocation, active Social/Court/Ranked private views and unchanged financial ledger/refund/recovery records.
6. Enable one bounded daily invocation, then monitor failed/skipped/deleted/redacted counts, cron exit code, backlog and DB latency. A larger backlog requires deliberate additional bounded runs, never a migration/startup purge.
7. Stop the schedule if unexpected counts/history issues appear. Code rollback does **not** restore deleted private links or credentials. Recovery needs a protected database backup; restoring obsolete credentials/votes requires careful isolation and must not revive revoked access. Restoring only minimum result metadata is preferable. No rollback auto-restore is implemented.

Do not print DATABASE_URL, tokens or private payloads during rollout. Financial storage has no destructive short TTL. Its eventual accounting/legal duration requires business/legal confirmation; this policy neither invents a statutory period nor claims legal compliance. M13/M14/LOW/CSP and account-deletion/product changes remain outside E-1.
