# Private OCI Staging runtime templates — NOT a deployment

These files are review-only examples for a **private-network/VPN** access option. They do not create instances, install units, reserve IPs, acquire TLS certificates, enable services, expose ports, use payment services, or touch Oracle. The owner must separately approve actual topology, costs (including network/VPN/TLS/backups), domain and access method. If the owner instead chooses an authenticated browser gateway, stop and review a different ingress design; this Nginx example alone is **not** browser authentication.

## Proposed process boundary

- Node 24.19.0 on a supported Ubuntu LTS **ARM64** image: confirm the actual `/usr/bin/node` path and installed version before use.
- A dedicated non-login OS principal `quddam-staging`; independently built and reviewed application under `/opt/quddam-staging/qalba-platform`. The process is **not root** and the source/build should remain operator-owned, not writable by the service account.
- A private staging-only PostgreSQL 17 database/user, optionally the separate `docker-compose.staging.yml` (never merge it with the development compose file), bound on IPv4 loopback; independently verify DB identity, migrations and disk use. Its Docker environment variables are separate from the application `DATABASE_URL` and must be managed securely by the operator.
- `quddam-staging.service.template` launches `scripts/start-staging.mjs`. That script loads Next's production environment first, executes the existing isolated staging preflight plus **private-network** and **AUTH_TRUST_PROXY=false** gates, and only then invokes the existing production launcher with **127.0.0.1:3000** explicitly pinned. It never runs migrations/seeding or enables payment; a passing configuration check is not network isolation proof.
- The service has basic systemd restrictions and allows writes only to designated state/cache and the pre-existing `.next/cache` directory. The actual Next runtime may need additional approved write locations (e.g., ISR); exercise actual flows **before enabling the service**, do not disable hardening broadly to make a failure disappear. Ensure compiled artifacts are not editable by the service principal. Template hardening must be adapted and verified against the chosen host's systemd version.
- `nginx-private-https.conf.template` must **only** be rendered after the owner selects an actual private VPN interface IP, verified staging hostname, valid TLS certificate/key and reviewed VPN/NSG/OS firewall rules. Replace `__PRIVATE_VPN_IP__` and `__STAGING_FQDN__` deliberately; private DNS alone is not access control. It deliberately has no IPv6 listener (deny any unapproved IPv6 ingress at NSG/OS levels). No automatic certificate provisioning or public port opening is implied.
- Nginx forwards a fixed approved Host / HTTPS origin and clears untrusted `Forwarded`, `X-Forwarded-For`, `X-Real-IP` and `X-Quddam-Client-IP`. Keep `AUTH_TRUST_PROXY=false`; rate-limiting then uses a conservative shared unknown-client bucket, which may constrain multiple invited testers. Never enable trusted-proxy mode from this template alone. SSE buffering is off; test reconnection and backend/proxy timeouts.

## Operator approval and acceptance sequence (not executed by these files)

1. Record owner's separate authorization of the actual resource/price envelope, tenancy Home Region, compartment, shape/boot storage and cost of all dependencies. Verify Always Free entitlement **as opposed to the higher regional quota**, and real A1 host capacity. No paid fallback or Free Trial credit reliance.
2. On the approved host only: confirm ARM64 architecture, Node location/version, PostgreSQL 17 compatibility, project dependency install, Prisma generate, Next build and application file ownership. Never use production data or merchant credentials. A migration operator independently verifies a **new isolated** staging DB and applies its forward-only migration inventory once; demonstrate transaction tests and restore into a *different* disposable database before any test deployment.
3. Prepare `/etc/quddam-staging/app.env` outside Git with `root:root 0600`; do not paste secrets into chat, CI logs or unit files. It must contain the approved staging `APP_URL`, expected origin/database, isolated DB URL, separate rate-limit secret, disabled welcome grants and **no** merchant, payment cron, SMTP, analytics cron, bootstrap or seed credentials. `NODE_ENV=production`, `STAGING_PROVIDER=oci`, `STAGING_CONTEXT=isolated-preparation`, `STAGING_ACCESS_MODE=private-network`, `AUTH_TRUST_PROXY=false` must all pass preflight. `STAGING_ISOLATION_OWNER_APPROVED=true` is a declaration that follows independent evidence, not a shortcut.
4. Review all proxy and service substitutions; make any required runtime cache write paths narrowly scoped. Run `systemd-analyze verify` and `nginx -t` on installed, substituted candidate files **without starting anything**. Review duplicate public/wildcard listeners and default virtual hosts. Admin access should be via owner-approved Bastion/VPN; verify egress and IPv4/IPv6 ingress separately.
5. **Only after separate launch approval** install/start service and the private ingress. Inspect `ss -lntp`, service user/permissions and effective NSGs, security lists and OS firewall. Expect only loopback `127.0.0.1:3000` and `127.0.0.1:5432`, with HTTPS on the **approved private VPN IP**, no public 22/3000/5432/443 and no unreviewed IPv6 bind. From an untrusted external network, connection attempts to direct app, DB and private HTTPS must fail; an authenticated VPN user should reach the approved canonical HTTPS origin with valid TLS. Test malformed Host, forged client IP headers, anonymous/non-VPN denial, SSE and restart persistence. Keep `AUTH_TRUST_PROXY=false` until a separately reviewed trusted proxy implementation exists.
6. Check running memory, CPU, DB pool, SSE polling, disk space/WAL/log retention, 429 rates and backup/restore alerts under modest synthetic load. Record anonymized proof against the exact source SHA and a GO/NO-GO review.

**No `systemctl enable`, `docker compose up`, `nginx reload`, `terraform apply`, real `prisma migrate deploy`, or Oracle operations occur in GitHub CI.** CI only validates fail-closed logic and static templates with synthetic values. It cannot prove VPN security, valid TLS, A1 capacity, real ARM64 compatibility, or restore ability.
